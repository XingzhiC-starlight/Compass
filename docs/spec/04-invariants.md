## §4 Core invariants

Code: `src/lib/db.ts`, `src/lib/supabase.ts`, `src/lib/localClient.ts`, `src/lib/localDatabase.ts`, `src/lib/transforms.ts`, `vercel.json`, `vite.config.ts`, `desktop/main.ts` · Keeps: I1–I21

The rules the code keeps, one row each. Cite them by ID; the Where column names the code that
keeps each rule.

| ID | Invariant | Where |
|---|---|---|
| I1 | **The seam.** Components reach the database only through `src/lib/db.ts`; DB-free pure logic lives in `src/lib/transforms.ts`, the other pure modules of `src/lib/` and the small pure modules beside each component. In the app, only `db.ts` imports `src/lib/supabase.ts`, and only `supabase.ts` imports the local database, `src/lib/localClient.ts` and `src/lib/localDatabase.ts` (I19); the desktop app's main process, which is not part of the page, runs the same engine (I20); the test support for the database checks, `src/lib/practiceCopy.ts`, reaches the same client and is never imported by the app (§19). | `db.ts` · `scripts/what-the-code-holds.ts` |
| I2 | **Owner-only RLS, anon key only.** With a Supabase project behind the seam (I19), every table is default-deny with four owner-scoped policies on `user_id`. The frontend holds only the anon/publishable key; the `service_role` key never touches code, env files or git — and never a `VITE_`-prefixed name, because Vite inlines every such variable into the public bundle. | `0001_init.sql` header · `supabase.ts` |
| I3 | **Per-project filter.** Every per-project read and every sibling-counting write filters by the active project id, because RLS cannot catch a missing project filter — a user owns all their projects. By-id writes rely on ids being globally unique. Reads of the project list are user-wide, and so is `listProjectCompletion`, which reads every project's phases to mark the finished ones (§6). One sibling count is not project-filtered: when a thought is dragged into a group, its place is counted from the group's members by `group_id` alone; a group id belongs to one project, so the count is project-scoped indirectly. Two time writes are user-wide on purpose: `startSession` closes running sessions across all of the user's projects, so at most one clock runs app-wide, and `closeStaleSessions` caps past-day sessions user-wide before every time read and before `startSession`. `stopSession` and the manual total replacement do not call it: the stop closes only the active project's sessions, capped by the same day-end rule, and the edit touches only the day it edits. | `db.ts` `requireActiveProjectId` · `listProjectCompletion` · `startSession` · `closeStaleSessions` |
| I4 | **Local-day contract.** The four `date` columns hold a local calendar day (`yyyy-mm-dd`) that the client writes: today's, from `todayDate()`, or the edited day's when a past day's hours are changed by hand. They are never compared with a server UTC day. Day boundaries in the UI follow the same local calendar, so the clock and the day counts roll at the user's local midnight; the task list never rolls (I10). | `0001_init.sql` header · `transforms.ts` `localYMD` |
| I5 | **One redirect contract.** Google sign-in, email confirmation and password reset all send `window.location.origin` as the redirect (`redirectTo`, and `emailRedirectTo` for the confirmation sent at sign-up and on resend); every served origin must be in the Supabase redirect allowlist. | `db.ts` `signInWithGoogle` · `signUpWithEmail` · `resendEmailConfirmation` · `sendPasswordReset` |
| I6 | **Turnstile key split.** `VITE_TURNSTILE_SITE_KEY` is public and lives in env; the Turnstile secret lives only in Supabase's bot protection settings. The widget renders only when the site key is present. | `src/auth/AuthTurnstile.tsx` |
| I7 | **Strict CSP.** `vercel.json` allowlists the Supabase host and `challenges.cloudflare.com`; `'unsafe-eval'` is never added to silence third-party console noise. The session token lives in `localStorage`, readable by any script that runs, so keeping scripts out is the real defense against token theft. | `vercel.json` · §17 |
| I8 | **Design units only.** Visual choices use the tokens and ratified scales in `DESIGN-SYSTEM.md`; for the units its census tracks, the only literals are its sanctioned exceptions. | `DESIGN-SYSTEM.md` D1 · D4 |
| I9 | **State-based routing.** `App.tsx` switches screens from state; there are no routes and no router library, and the dashboard's summary/depth is a state toggle, not a route. The privacy notice is a static page of its own (§14). | `App.tsx` |
| I10 | **Tasks persist across days.** The task list is never filtered by date; `task_date` is provenance only. | `db.ts` `getProjectDashboardData` (the dashboard's read) |
| I11 | **Remount-on-load lives in Dashboard.** `App` does not key `Dashboard`; a load — the first open, a project switch, "Try again" — remounts the card tree through a Fragment keyed by `projectCardTreeKey(id, version)`, so no per-card state crosses projects. A quiet refresh after a failed save keeps the key: the cards adopt the refreshed payload in place (`syncVersion`, `useServerState`), so open boxes, the cursor and a selection survive. A stale-request guard drops any payload, loaded or refreshed, from a superseded request. | `src/dashboard/Dashboard.tsx` · `dashboardLoad.ts` · `useServerState.ts` |
| I12 | **Lazy Supabase client.** `getSupabase()` creates the client on first use, never at import time, and creates it once: the Supabase client or the local one (I19). Importing `db.ts` therefore reads no setting and creates no client; the one thing it reads is the remembered active project (§21). | `supabase.ts` |
| I13 | **IME-safe Enter.** Every inline edit field submits through `isSubmitEnter()`, which ignores the composition-confirm Enter of CJK input methods. | `src/dashboard/keys.ts` |
| I14 | **Numbers are text.** The numbers on the cards render as text. Those a person can change (today's hours and the goal, a past day's hours, a phase's days, a learning item's percent) become an input only while being edited, never an always-on input. | `DESIGN-SYSTEM.md` D5 |
| I15 | **CSlider drags from window-level pointer listeners**, not `setPointerCapture`, and swallows the click the browser synthesizes after a drag so it cannot flip the dashboard view. | `src/dashboard/CSlider.tsx` |
| I16 | **Dormant columns are deliberate.** `total_days` and `hours_available_per_day` hold two setup answers that no screen reads, and `daily_tasks.phase_id` and `learning_item_id` are always saved empty; all four stay in the schema for the ideas in `docs/ideas.md` (§3). | `0001_init.sql` |
| I17 | **`user_id` is stamped by the database.** Inserts never send it; the column default is `auth.uid()`, and the local database stamps its one person (I19). | `0001_init.sql` · `localDatabase.ts` · the inserts in `db.ts` |
| I18 | **The dev port is 5173, and the practice app's is 5183.** The first is fixed in `vite.config.ts` (`strictPort`): when 5173 is busy the dev server refuses to start rather than moving to another port, because only that origin is in the Supabase redirect allowlist. The practice app (§19) is held the same way at an address of its own: it refuses to start when 5183 is taken, never moves to another and never uses an app already running, and that origin is the one entry in the practice copy's redirect list. Each of the two listens where the machine resolves `localhost`, one of its two loopback addresses. The dev server's refusal holds there alone: a program that holds 5173 on the other loopback address does not keep it from starting, nor, on macOS, one that holds it on every address of the machine. The practice app first asks both loopback addresses, 127.0.0.1 and ::1, whether anything answers at 5183, and refuses when either does, so a program on either address alone, or on every address, keeps it from starting; it asks only as it starts, so a program started at 127.0.0.1:5183 after it is up is not stopped by it. So both can run at once, and with nothing else started at either port the address alone says which database is behind a page. | `vite.config.ts` · `scripts/practice/cli.mjs` · `supabase/config.toml` |
| I19 | **Two databases, one seam.** What stands behind the seam is decided once, by the two values the build was given; a value left empty counts as not given, the same as one never set. With both `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`, `getSupabase()` hands back the client of that Supabase project. With neither, it hands back the local client, which keeps the seven tables on this device and has no accounts: one person is always signed in, who that is never changes, and no request leaves the device. With one of the two alone it throws, naming both, and makes no client. The local client answers the calls the seam makes in the shapes the Supabase client answers them, and keeps the rules the schema keeps (§3), so the seam is the same code over either. Inside the desktop app it is the local client always, whatever the two values are (I20). A screen learns which of the two it is over only from the seam's `storesOnThisDevice()`. | `supabase.ts` · `localClient.ts` · `localDatabase.ts` · `db.ts` `storesOnThisDevice` |
| I20 | **The desktop page is only a page.** In the desktop app (§22) the page has no Node, no Electron and no disk: context isolation and the sandbox are on, and what it is given beyond a web page's own is `window.compassDesktop` with two functions: `send`, which hands a request for the local database to the main process, and `show`, which asks for the main window to be shown and carries nothing. The one window the page may open is its own companion (§23, I21), empty, and that window's document is given no bridge. The main process is the data file's only reader and writer, answers only the app's own page, serves the page from the app's own folder under a policy that lets it connect to nothing, and never starts a second copy of itself. The desktop app has no accounts and is never over a Supabase project. | `desktop/main.ts` · `desktop/preload.cjs` · `desktop/dataFile.ts` · `desktop/appFiles.ts` · `supabase.ts` |
| I21 | **The companion holds nothing of its own.** The companion (§23) is not a second page: the main page draws it into a small window through a React portal, so it reaches the data only through the seam (I1) and stores nothing anywhere. Where it repeats a card's line or bar (the Commitment card's line, the Timeline's and the Learning card's glance) it calls the card's own function in `src/dashboard/projectTime.ts`. Neither window is handed what the other changed: the companion reads again whenever the saves in flight have all answered, and after a save of its own it asks the dashboard for a quiet refresh, so each shows what is stored. The dashboard owns the window: one at a time, for the active project, closed when the dashboard goes. | `src/companion/Companion.tsx` · `src/dashboard/Dashboard.tsx` · `src/dashboard/projectTime.ts` · `db.ts` `onSavesSettled` |
